## G-01：厳密解析と値を失わない生成

### 選定候補と方法

`jsonc-parser@3.3.1`（MIT）を字句位置付き構文木の候補とした。コメント等を許すパーサーの機能をそのまま受付条件にせず、`disallowComments`、末尾カンマ不可、空内容不可と**全解析エラーの確認**を必須とした。ライブラリの回復結果を成功として採用しない。公式にもエラー一覧の確認が求められる。[公式README](https://github.com/microsoft/node-jsonc-parser)

数値はパーサーの数値化済み`node.value`を出力へ使わず、元文字列のoffset／lengthからトークンを取得する。オブジェクトのchildren順を使い、復号済みキーのSetで重複を検出する。再帰パーサーへ渡す前に深さ・ノード数を走査する。

### 結果

- 6種類のルート、BOM付きUTF-8、日本語・半角カナ・絵文字・空コンテナーを受理。
- 不正UTF-8、UTF-16／32のBOM、コメント、末尾カンマ、複数文書、不正数値、重複キー、孤立サロゲートを拒否。部分選択の外側にある重複キーも拒否。
- `9007199254740993`、`-0`、`1.2300`、`1e400`と数値風キーの入力順を保持。
- 空キー・`/`・`~`・実改行／タブ・バックスラッシュ+n/tのPointerを、Markdown AST、plain text、JSON復号、値の再解決で区別。
- 一覧表のキー和集合、入力順、欠損／null／空文字、ネスト値、システム列と同名のキーを区別。
- 深さ128／129、100,000／100,001ノード、表10,000／10,001行、100／101列、図200／201ノード、ラベル199／200／201、コード49,999／50,000／50,001、50 MiB入力、Markdown本文10 MiBの一致／超過を検査。
- JSONだけの解析・3スタイル生成では、4ブラウザともanydoc／PDFiumのWASM取得なし。
- 大量のバッククォートや多数ノードを関数引数のspreadへ展開しない走査にし、100,000ノードと大量の短いバッククォート列も4ブラウザの実Workerで確認した。

自動検査は**21件成功・0件失敗**。図については別途4ブラウザで実描画の全ラベル一致、200ノード・199エッジを照合した。ノード数の一致だけを完全性の証明にしていない。

### 検出して修正した試作上の問題

1. **Markdown自動リンク化**（実装問題）: 文字参照によるエスケープだけではGFMの自動リンク処理を抑止できず、URLを含む値がリンク化された。既知のセルとASTを比較したことで検出した。動的な長さのコードスパンと表のパイプ処理を使い、セル文字列・plain textの一致を再確認した。
2. **Mermaidの文字参照と既定Markdown解釈**（実装問題）: 文字参照が表記のまま残る候補と、ノード属性の既定Markdown解釈で内容が変わる候補を検出した。ノード属性に`labelType: text`を明示し、キー・値はJSONとして可逆な表記に変更した。制御文字等は元のコードポイントからUnicodeエスケープを生成し、既存のエスケープを誤って二重変換しない。
3. **長さの単位差**（実装問題の予防）: アプリのコードポイント上限とは別に、ライブラリ側のUTF-16単位の上限を考慮した。50,000コードポイントを独立に検査し、ライブラリ側はその最大100,000コード単位に合わせた。34,775コードポイント／54,675コード単位の図が、200ノード・199エッジ・全ラベル一致で4ブラウザとも成功した。

Mermaidの文字参照とノード属性構文は[公式Flowchart仕様](https://mermaid.js.org/syntax/flowchart.html)、ノード属性のlabelType既定動作は[固定版のFlowDb実装](https://github.com/mermaid-js/mermaid/blob/mermaid%4012.2.0/packages/mermaid/src/diagrams/flowchart/flowDb.ts)も参照した。出力先のMermaid版との互換性は、製品へ採用する際に別途確認する。

## G-02：1解析セットと回復

### 状態の確認

元Fileと確定設定・完了結果をUIに残し、完全な解析セットはWorker内の1件だけとした。別ファイルへの切替で追い出し、必要時に再解析する。

実PDF30ページを既存anydoc変換経路で通常変換できることを対照検査した。その後、JSON Aを完了→PDF Bの変換経路開始→Worker破棄→A/C再解析を行い、Aの結果・確定対象を保持し、Bをcancelledにできた。Cの`/results`を生成し直し、C固有の`1.2300`が残り、A固有の数値が混入しないことも対象ケースで確認した。

20回の連続検査、巨大文字列の10,000コードポイント抜粋、構文不正からの再試行、Worker異常からの再生成も成功した。古いWorkerの応答は世代と要求IDで受け付けない。

| ブラウザ | 取消操作の同期フィードバック | A/C再検査の所要時間 |
| --- | ---: | ---: |
| Chrome | 約0.6 ms | 約12 ms |
| Edge | 約1.1 ms | 約14 ms |
| Firefox | 約2 ms | 約49 ms |
| WebKit | 約1 ms | 約95 ms |

上記は小さい合成入力で、処理開始通知を受けて取消ボタンのハンドラーを実行した測定値。入力全般や実端末の性能保証ではない。

### メモリの測定

Chrome CDPの`Runtime.getHeapUsage`でUIとJSON Workerを別々に測定した。次は概数であり、明示GC後の診断値を含む。

| 状態 | WorkerのusedSize | WorkerのbackingStorageSize | 保持解析セット |
| --- | ---: | ---: | ---: |
| 初期 | 0.27 MiB | 0.02 MiB | 0 |
| 1 MiB入力・1回目、GC後 | 0.33 MiB | 1.02 MiB | 1 |
| 同程度の入力・20回目、GC後 | 0.38 MiB | 1.02 MiB | 1 |
| 8 MiB入力、明示GC前の標本 | 0.39 MiB | 16.02 MiB | 1 |
| 同入力、明示GC後 | 0.38 MiB | 8.02 MiB | 1 |
| 大きい解析木を追い出した後、GC後 | 0.39 MiB | 0.02 MiB | 1（小さいA） |

20個の解析木が蓄積する挙動は見られず、大きい解析セットの解放傾向を確認した。ただし**これは真のピークやプロセス全体の常駐メモリではない**。File／Blobのネイティブ領域、図・WASM、最大件数の大きい完了結果、OSのメモリ制約をすべて含む保証ではない。iPhoneでの最悪条件と総メモリは未確認のため、G-02全体は保留とする。

## G-03：選択と閲覧を分けたツリー

4ブラウザで、次の対象ケースが成功した。

- 矢印の開閉で選択・スタイルを変えず、ラジオで対象を変える。
- `/results`＋一覧表→`/summary`で不適合→`/results`へ戻すと、同じスタイルのまま判定後に決定可能になる。
- 取消で確定設定・旧結果を維持する。
- 300行の表示窓から外れた選択を保持し、Tabだけでは変えない。
- 「選択位置を表示」で祖先・階層内のページ・表示窓を復元し、対象がDOMに現れてからフォーカスする。51番目の兄弟も到達可能。
- 深さ128でも字下げを64px以内に抑え、320pxで画面全体の横はみ出しを起こさない。
- 深い対象へ移動した場合も決定・取消を画面内に維持する。本文スクロールとフッターを分離し、両ボタンの画面内座標を4ブラウザで確認した。
- 640px幅で本文・ラベルを32pxに拡大し、実際のcomputed styleも確認して取消を操作できる。

実ページズーム200%、OSの文字拡大、iPhoneの縦横切替・タッチ、実スクリーンリーダーは未実施。これらとネイティブラジオの実機動作がG-03の残る条件である。試作は画面設計の全項目を完成させたUIではない。

## G-04：未達の詳細

### 成功した安全性・失敗制御

`mermaid@12.2.0`（MIT）を固定し、strict、HTMLラベルなし、連番ノードID、入力のtext扱いを使用した。検証済みのコードだけを描画へ渡し、iframeは`allow-scripts`のみ、出所ウィンドウ・nonce・描画世代を照合した。生成SVGのscript／foreignObject／a／image等と外部参照も検査した。

4ブラウザで次を確認した。

- HTML・画像・リンク・設定命令・コードフェンス・引用符・メタデータ風の文字列をデータとして扱い、全ラベルが期待表記と一致した。
- 200ノード・199エッジと全ラベル一致。実行時の外部要求は0件。
- 検証用Worker資産を取得できない冷状態では出力を停止し、「図を再試行」も許可しない。通信を戻すだけでは復活せず、明示的な生成・検証で回復する。
- 検証済み本文がある状態の図表示失敗では、出力許可を維持する。クリアでは失効させる。
- localStorage／sessionStorage／IndexedDBへの保存なし。Cache APIは静的資産だけで、クエリ付きURLや入力・結果・設定を保存していない。

厳格設定だけで安全性を保証したとはせず、[公式Usage](https://mermaid.js.org/config/usage.html)に沿った設定と、実生成物・要求の両方を確認した。

### 未達1：親UIを止めずに5秒で中断できない環境がある

初期化済みの描画コンテキストに有限6500msの同期負荷を与え、親が5秒のタイマーで破棄できるかを検査した。

| ブラウザ | 親の中断タイマー実行まで | 100ms周期の親tick | 判定 |
| --- | ---: | ---: | --- |
| Chrome | 約5001 ms | 50 | 対象条件では中断できた |
| Edge | 約5004 ms | 50 | 対象条件では中断できた |
| Firefox | 約6508 ms | 2 | **未達。負荷が終わるまで親も応答できない** |
| WebKit | 約6526 ms | 2 | **未達。同上** |

Firefoxでは対象ケースを独立再実行して再現し、スクリプトも終了コード1となった。タイムアウトの延長は行っていない。

この負荷は「あるJSONが実際に6500ms掛かる」という再現ではなく、**選んだ隔離コンテキストの実効中断能力**の検査である。G-04が要求する長時間描画への回復を証明できず、親UI停止・キャンセル不能の重大リスクが残る。分類は隔離方式の実装・設計上の不足と実行環境差であり、Safari製品全般の不具合とは断定しない。

### 未達2：取得済み資産でもオフライン再描画に失敗する

同じコンテキストで一度描画成功し、静的キャッシュを作った後にオフラインへ切り替え、新しい隔離iframeで再描画した。

| ブラウザ | 結果 |
| --- | --- |
| Chrome／Edge | `/frame.html`の取得が`ERR_INTERNET_DISCONNECTED`となり、15秒で初期化タイムアウト |
| Firefox | 図を再表示できた |
| WebKit | `/frame.html`の取得で内部エラーとなり、15秒で初期化タイムアウト |

検証済み本文の出力許可は維持され、未検証本文を公開する誤動作は検出しなかった。しかし取得済み資産でのオフライン図表示は、現候補では成立しない。

隔離iframeのナビゲーションとService Worker／キャッシュ適用の組合せが調査対象になる。正確なブラウザ内部の原因までは確定しておらず、単なる資産未取得やブラウザ固有バグと断定しない。

## 次に進める範囲

1. JSON解析・表生成の候補とテスト資産は保持する。ただし今回の検証だけでproductionへ組み込まない。
2. G-04は、重いレイアウトを独立Workerへ移せる方式、または同じローカル資産で中断・オフラインが両立する別の描画方式を比較する。現時点では候補であり、実現できると断定しない。strictや完全性を緩めて回避しない。
3. 新方式でも、同じ6500ms負荷、全ラベル・ノード・エッジ照合、取得済み／未取得オフライン、再試行・クリアを再実行する。
4. 対応する実端末で、ピークメモリ、操作300ms／取消1秒の目標、Safari、読み上げ、PWA更新を確認する。G-04が成立しない場合の仕様変更は、両文書に理由を記録した上で別途決定する。

本体の変更、公開、PR作成、デプロイは行っていない。
