## 判定

**Firefoxの初期化期限精度と、WebKitのオフラインページ再読込は、今回のWindows検証環境で解消した。4ブラウザーの対象E2Eは48件すべて成功。本体への統合は引き続き保留する。**

Firefoxは単発タイマーへの依存を改めた。WebKitは試作内の検証環境を修正済みのPlaywrightへ更新した。本体の処理・SW・依存、要件・画面設計の本文は変更していない。

この判定は今回の残件に対するもの。実macOS／iPhone Safari、インストール済みPWA、独自SVG表示方式の採用・CSP等が未確認のため、G-04全体通過・本体統合可能とは判定しない。

## 1. Firefox: 長い単発タイマーの配送遅延

### 切り分け結果

旧Playwright `1.62.1`・Firefox `153.0`の前面表示タブで、同じ15秒を異なる監視方法で各2回、条件ごとに逐次測定した。

|監視条件|1回目の実測|2回目の実測|観測|
|---|---:|---:|---|
|単発のsetTimeout(15000)のみ|16,501ms|16,242ms|15秒より大きく遅れて通知|
|50ms以下の短周期監視を併用|15,000ms|15,000ms|期限付近で通知|
|独立Workerの単発タイマーを併用|16,229ms|16,250ms|Workerへ移すだけでは遅れが残る|

performance.nowとDate.nowの経過時間は概ね一致し、visibilityStateはvisibleだった。単純な時計単位の取り違えや背景タブだけでは説明できない。Firefox／Windows内部の遅延機構までは断定しないが、この環境で長い単発タイマーの通知が遅れることと、短周期監視で改善することを再現できた。

実装上の問題は、初期化の終了判定が単発タイマーの配送だけに依存し、非同期応答の採用時にも絶対期限を確認していなかったこと。環境差で顕在化する実装上の弱点として修正した。独立した時計Workerの追加は、対照測定で効果がなく構成も増えるため採用しなかった。

### 改善

- `deadline.mjs`で、単調増加する時計から絶対期限を算出し、最大50ms周期で到達を確認する。
- ready、構文検証結果、配置結果、SVGの途中処理・確定時にも期限を確認し、通知が遅れた場合も期限後の結果を採用しない。
- 初期化15秒・描画5秒の予算は維持する。試験許容値も変更しない。
- 中断・クリア時に監視を解除する。遅れて完了した旧資材取得が新世代のWorker参照を上書きしないようにする。

SDK更新の効果と分けるため、**旧Firefox 153でも修正後の試作を検証し、15,001msでの中断・出力保持・再試行成功を確認した**。最終通し実行のFirefox 157も15,001msだった。

タイマー配送前に同期処理で期限を超える検査、通知の一回性、取消後の非通知を単体検査した。さらにALT-12では旧資材取得を遅延させ、新世代の重いWorkerをクリアした後にWorkerが残留しないことを4ブラウザーで確認した。

## 2. WebKit: オフライン模擬側の問題

### アプリと切り離した対照

アプリ、Cache API、変換処理を一切使わず、SWが固定HTMLを返すだけの独立サーバーで比較した。各条件は新しいオリジンとコンテキストで実行し、SWが制御していることを前提確認した。

|環境|通常|setOffline(true)|接続先サーバーを実際に停止|
|---|---|---|---|
|Playwright 1.62.1 / WebKit 26.5|成功|遷移失敗|成功・SW応答|
|Playwright 1.64.0 / WebKit 27.2|成功|成功・SW応答|成功・SW応答|
|Chrome・Firefoxの修正版SDKでの対照|成功|成功・SW応答|成功・SW応答|

SWなしの負の対照は、模擬オフライン・サーバー停止のどちらでも期待どおり失敗した。SW応答の成功時はHTTP 200、fromServiceWorker=true、障害中の接続先受信件数0を確認した。

加えて、**旧WebKit 26.5でビルド済み試作の資材を取得し、配信サーバーを停止した後も、ページ再読込・JSON再生成・図表示に成功した**。追加した一時fixtureは再読込後に復元されず、入力永続化を回避する前提も維持した。したがって、今回の再読込失敗をアプリのキャッシュ不備とする根拠は得られなかった。

Playwrightには同じ固定SW応答でもオフライン模擬で遷移が拒否される[公式の不具合報告 #42775](https://github.com/microsoft/playwright/issues/42775)があり、[修正PR #42894](https://github.com/microsoft/playwright/pull/42894)がマージされている。今回の新旧対照はこの修正内容と整合する。原因分類は**検証環境の問題（Playwrightと同梱WebKitのオフライン模擬）**とし、実Safariそのものの不具合とは扱わない。

### 改善と区別した条件

- 試作フォルダーだけに `@playwright/test=1.64.0` を固定し、対応するFirefox／WebKitを準備した。rootの依存定義・lockfile・ブラウザーSDK実体は変更していない。
- `browser-runtime.mjs`で新旧SDKを明示選択し、証跡へSDK・ブラウザーバージョンを記録する。旧ブラウザーを残し、新版だけで過去の結果を上書きしない。
- 修正版で、ビルド済み試作のsetOffline→ページ再読込→新JSON Worker生成→構文検証→図表示が成功した。オフライン再描画だけの成功で代用していない。
- `route.abort()`によるHTTP遮断は、新版WebKitでも固定SW応答の遷移が失敗した。これはsetOfflineとは異なる自動化条件として記録し、通信断の証明や成功の代替には使わない。今回の判断には、setOfflineと実際の接続先停止の別々の対照を使った。

接続先停止は端末全体の通信断と同義ではない。オフライン模擬と対照を組み合わせた今回のWindows結果を、Safari実機やインストール済みPWAへ一般化しない。

## 3. 最終の通し確認

Playwright `1.64.0`、Windows、headless、新規コンテキスト、専用ポート4187。合成fixtureのみを使用し、同一実機では対象スクリプトを一つずつ完了させた。

|ブラウザー|描画中断の実測|親UIの100ms応答回数|初期化中断の実測|オフライン再読込・再生成|成功数|
|---|---:|---:|---:|---|---:|
|Chrome 155.0.8059.85|5,000.8ms|50|15,007.8ms|成功|12 / 12|
|Edge 155.0.4283.62|5,000.8ms|50|15,004.6ms|成功|12 / 12|
|Firefox 157.0|5,000ms|50|15,001ms|成功|12 / 12|
|Playwright WebKit 27.2|5,009ms|46|15,013ms|成功|12 / 12|

**合計48件成功・失敗0、終了コード0。** 初期化の許容は前回と同じ14,900ms以上15,300ms未満、描画は4,900ms以上5,300ms未満。経過時間の表示・許容を変えて成功にしたものではない。

試作ビルド成功。既存の厳密解析・生成検査21件と追加の期限検査2件を、並列化せず23件実行し全件成功。文書検査も25文書・58ローカルリンクで問題0だった。SDK追加時の依存監査は122パッケージ・指摘0。検証後に専用サーバーは停止した。

実行対象はALT-01～12。危険文字列、全ラベル・全辺の一致、200ノード境界、描画中断、旧図排除、オフライン新Worker・再検証、検証失敗時の出力禁止、描画のみ失敗したときの検証済み出力保持、資材取得失敗、15秒初期化、未取得オフライン、ページ再読込、新旧初期化競合を含む。外部HTTP要求0、localStorage／sessionStorage／IndexedDBへの入力・結果保存なし、静的資材のみのキャッシュも確認した。

E2E範囲は**変更したG-04対象ケースのクロスブラウザー**。本体統合を行っていないため既存アプリの全E2E、G-01～G-03のブラウザー全件、公開環境は対象外とした。製品の混在キュー全体、実ページズーム・読み上げ・タッチ・OSメモリ圧・バックグラウンド復帰は未実施。

前回の期限検査は遅延を検出できたが、短周期監視との対照がなく機構を絞れなかった。今回、可視状態・2種類の時計・複数監視方式を揃えた。SWについても前回はアプリの失敗までしか観測せず、固定応答・実配信停止・SWなしの対照が不足していたため、アプリ実装と模擬環境を分離できなかった。今回の最小再現とSDK版の記録を、同種問題の切り分けに再利用する。

まず防ぐべき致命的不具合は、未検証の出力、本文の送信・永続化、文書間混入であり、期限判定や環境更新によって緩和していない。今回の2件は対象条件で解消したが、独自SVG表示の採用判断、製品CSP、資材の最小化・更新設計、実Safari／実PWAの検証は保留を継続する。厳密な実時間保証ができないOS停止・JavaScript停止中も、復帰後に期限後の結果を採用しない設計を維持する。
