# 本体PWAの世代固定・更新回復検証（CUR-03）

2026-10-30。PR #21のhead `7fc91e3fc431e03ffaf3e14a43ae535d470905ed` とCI成功を確認してsquash mergeし、mainを `5ad41ecf2df8e68369948337b92529880f5113b4` に同期した。[マージ後CI #45](https://github.com/Bamboosato/local-document-preprocessor/actions/runs/41016607780)も成功。本変更は `codex/pwa-generation-recovery` のレビュー対象であり、まだmainに取り込まない。デプロイなし、macOS/iOS対象外、実機はユーザー別途。

## 観点・意図・前提

ケース詳細より先に[計画](pwa-generation-plan.md)の機能/非機能/データ/UI × 正常/異常/境界/状態遷移を固定した。最優先は致命な文書/結果の永続化、重大な世代混在・旧結果の無警告破棄・回復不能を防ぐこと。[ADR-0005](adr/0005-pwa-generation-cache.md)が設計の正で、旧独立SVG試作は再開しない。

自動ブラウザー検証はWindows、ローカル同一origin、新規context、合成JSONと既存の非機密fixtureを使用する。実際の本体ソースを一時ディレクトリへコピーし、見出しとJSON Workerの識別フィールドだけをA/Bで変更してビルドする。生成物は実ビルダーでハッシュ化し、HTTP配信先だけをA→Bに切り替える。元の製品ソースはfixture生成で変更しない。キャッシュ/登録の初期化と世代ID照合を各ケースで行い、同一端末のブラウザー実行はworkers=1で直列にする。

## 変更した動作

- 全配布静的資産をサイズ/SHA-256で列挙し、HTML・SW・公開manifestの世代IDを一致させる。今回のビルドは441資産、24,419,767 bytes（約24MB、SW自身を除き公開manifestを含む）。Worker・両WASM・Mermaid遅延chunk・ライセンス原文も事前取得する。JSON利用だけでもPWA準備の通信は発生するが、JSON処理でWASMを初期化しない。
- installは全資産検証後だけ完了標識を書く。旧Aの全タブ/PWAが終了するまで新Bは待機する。skipWaiting/clients.claim、自動reloadは使わない。新世代のHTML/JSを旧世代へ混ぜない。
- 欠損/破損時は同じハッシュ/MIMEの応答だけを修復に使用する。不一致は503にして誤った成功を防ぐ。文書・結果・設定は永続化しない。静的許可一覧外、POST、外部URL、クエリを新たな保存キーにしない。
- 画面は初回未制御、準備中、利用可能、更新待機、失敗、欠損、世代不一致を区別する。未知の旧SW/世代不一致では新しい変換を止め、既存入力/結果は消さない。初回未制御ページには保存後の明示再読み込みを案内する。
- HTMLも失われた場合は、限定nonce CSPの503復旧ページから新世代の準備を再試行できる。他タブの結果を保持したまま待機まで進め、全終了/再起動を案内する。通常アプリのCSPは変更しない。

### 失敗分析と再発防止

EdgeのPG-02で、更新失敗後に未完了のBキャッシュフォルダーが残り「Aフォルダーだけ」という初期テスト前提が成立しなかった。原因分類はテスト観点/状態前提の不足。ブラウザー側の中断・再インストール等のどれで残ったかは断定しない。新規に所有した失敗キャッシュは削除するが、既存キャッシュを壊さない設計なので、フォルダー存在を利用可能の証拠にしない。

取得故障が実際に発生した件数、installing/waitingなし、Aの完了標識とactive照会のcomplete、B完了標識なしを判定するよう修正した。修正後のEdge対象ケースは3回連続成功。残存Bは未公開であり、旧A結果を破棄する修正はしていない。中断された部分キャッシュが残る場合の追加容量も残存リスクとして扱う。

WindowsのVitestでfork起動前に期限超過する環境エラーが発生した。アプリのassertion失敗と分け、ワーカー1/ファイル並列なしで121件成功を確認した。プロセス起動失敗の根本原因は未確定で、タイムアウト延長による隠蔽はしていない。長時間テストはログファイルと終了状態を確認し、RPC期限だけで重複起動しない。

## ユーザー実機へ渡す手順（未実施）

前提はWindows Chrome/Edgeの専用検証プロファイル、ルート配信のlocalhostまたはHTTPS、合成fixtureのみ、保存済みの必要結果、同一端末の直列実施。productionへは配信しない。OS/ブラウザー版、コミット、公開manifestのID、fixture ID、操作順序、成否/時刻を記録する。証跡に文書本文/PII/不要なローカルパスを含めない。失敗時はCache件数/READYと登録のactive/installing/waitingの状態を記録し、結果保存前の全ストレージ消去はしない。

|順序・意図|操作と期待状態|
|---|---|
|1 初回準備/非制御の区別|オンラインで起動し準備完了を待つ。「次回起動用」と表示される初回タブでは結果保存後に明示再読み込みし、現世代準備済みになること。未完了時にオフライン対応済みと扱わない|
|2 未使用機能のオフライン起動|PWAをインストール、全終了後オフラインで起動。未使用のJSON/標準図、機械可読PDF/CSVを順に試し、原本/期待fixtureと照合する|
|3 複数タブと更新待機|Aで結果を作り別タブ/PWAも開く。管理された検証配信をBへ更新し、待機表示・A結果保持・Aの未使用機能を確認。一つだけ閉じても残るAを強制更新しないこと。保存後に全終了してB起動を確認|
|4 取得失敗/明示回復|専用検証配信でBの資産を一つ取得不能にし、A維持と失敗案内を確認。配信を修復して再取得し、B待機へ進むこと。オンライン復帰だけで結果を消さないこと|
|5 保存制限/容量不足|使い捨てプロファイル/VMで保存拒否や制限容量を用意。実環境を危険にするディスク全埋めはしない。準備完了を誤表示せず、旧結果を保持し、制限解除後に明示修復できること。再現できない場合は未確認と記録|
|6 OS休止/復帰/負荷|結果を表示したタブ/PWAを休止・復帰し、更新待機/通信断/低メモリ時を分けて確認。OSによるプロセス破棄後は文書を保存していないため復元できない。生存中の結果保持と混同しない|
|7 キャッシュ欠損/旧方式移行|結果保存後の専用プロファイルで対象資産またはindexだけを削除して失敗/復旧案内を確認。旧版からの移行は可能なら隔離した既存版プロファイルで別途実施。実施条件がない場合はfixtureの自動成功だけで完了にしない|

## 残件と判断範囲
