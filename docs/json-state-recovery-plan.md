# JSON 状態・保持量・故障回復の検証計画

PR #20 マージ後の CUR-02 を対象とする。新PRのマージ・デプロイ、macOS/iOS、実機操作は対象外。

## 先に確認する観点

最優先は、致命な文書間混入・未検証本文の出力と、重大な取消不能・失敗後回復不能・過大な保持を防ぐこと。

|区分|正常系|異常系|境界値|状態遷移|
|---|---|---|---|---|
|機能|ファイル別設定と完了結果を保持|構文検証資産失敗時は出力不可、表示だけの失敗では本文保持|空値・全方式不可|取消→必要時再解析、取得失敗→利用者操作で再変換|
|非機能|入力読込とWorker処理を逐次化、同一ファイル再利用|Worker異常・遅延応答・読込失敗・postMessage失敗|50MiB、10万ノード、20ファイル、300表示行|追い出し・取消・クリア後に再利用、反復時の保持傾向|
|データ|元数値字句とPointer、別文書の値を保持|違うfileId/要求/設定の応答を採用しない|巨大単一文字列・ノード超過|旧設定→新設定、A→B→Aの再解析|
|UI|処理中の確定停止、失敗理由と再試行|不適合のまま確定/コピー/DLできない|50KiB表示と生成上限を分離|古い詳細/図を破棄、完了済み別ファイルを維持、復帰だけで自動再開しない|

UI受入の照合で、UI-11 の結果表100行ページ分割も確認対象とする。表示を100行＋次ページに制御し、MD/TXTの全101行出力を別に照合する。ページ分割を本文の切捨てへ流用しない。

## 実行条件とケースの意図

合成 fixture だけを使い、新しいブラウザーcontextと状態初期化を前提にする。故障注入は serviceWorkers:block のcontextで対象worker/描画資産を識別し、注入件数を必ず照合する。タイムアウト延長で失敗を隠さない。ログはfixture ID・件数・状態・容量・成否を中心とし本文を出力しない。

単体では、読込待ちも含めた直列化、取消後の旧応答拒否、キャッシュ追い出し、同名Fileの分離、エラー後の回復、生成前の上限判定を確認する。対象E2Eでは、UI-26の「検証済み図だけ失敗」と「構文検証前に失敗」の両経路、20ファイル、応答逆転・再試行・クリアを通す。

最大負荷はブラウザーの合成50MiB/10万ノード入力、既存文書Worker・標準図・完了結果を含め、取得できるヒープ指標のピーク/破棄後傾向を測定する。GC後の数値やWindows headlessの成功を実機の安全上限と一般化しない。測定不能な領域と対象端末の負荷はCUR-05に残す。

worker通信・生成境界を変えるためChromiumは既存を含め全件回帰、Chrome/EdgeはJSONの対象ケースを順次確認する。同一端末でテストを並列実行しない。全UI-01〜26の証拠対応を報告書にまとめ、不足は明記する。
