## 実装と検出の意図

|変更|防ぐ問題・検証|
|---|---|
|JSON要求のFIFOと同一Fileの再利用|同時の全入力読込と毎操作の再転送を防止。別Fileへ移る前にWorkerのrelease応答を待つ。同名でも異なるFileは別ID。20ファイルの要求/転送を計数|
|中断可能な共通FileReader|JSONと既存文書の読込で取消と30秒期限を扱う。取消後に旧読込が新Workerへ投稿されない。注入readerが中断を無視する単体条件でも、settle前に次の入力を読み始めない|
|応答の照合|要求ID・operation・File ID・解析世代・Pointer/方式と、閉包のWorker世代を照合。Appの検査世代・runId・設定版も維持。違うFile/設定/解析世代のpayloadを成功にしない。終了済みWorkerの遅いerrorでも新要求を取消さず、破棄済み文書clientを再生成しない（SR-04/30）|
|変換失敗後のWorker破棄|資産のdynamic import失敗を保持したWorkerを次の再試行に使わない。利用者の再確定・実行で新Workerを生成。オンライン復帰だけでは自動再開しない|
|既存文書Workerのerror|終了済み/破棄済みWorkerのerrorを無視し、資産取得失敗での自動生成ループを防止。次の明示要求でだけ再生成する（SR-30）|
|初期設定の生成可否|解析成功だけで初期「全体/項目表」を待機扱いにしない。上限超過は設定変更可能なエラーとし、全部不可なら入力の分割・縮小を案内|
|詳細取得の再試行|現在の失敗時は古い詳細を破棄し確定停止。「JSONを再読込」と、明示的なルート選択を提供。取消では確定設定と過去結果を保持|
|生成の保持抑止|compactの累積UTF-8予算、表の行追加中の予算、構造図の先頭201ノード判定と巨大ラベルの事前判定。上限超過を部分成功にしない。適合判定は一つのWeakRef対象の小さな結果だけ再利用|
|JSON表の100行ページ|Markdown解析前に現在ページ100行だけを抽出する。1ページ50KiB超はソース先頭10,000文字の抜粋と明示。JSON plain textも50KiB超は抜粋表示。MD/TXTのコピー・DLは本文全量。101行のコピー（メモリstub）・実DLと、9MiB値の実DLを照合|
|ダイアログのフォーカス復帰|取消/確定で接続中の起点要素へ戻す。Tab/Shift+Tabは選択を変えず、モーダルの外へ出ないことを対象E2Eで確認|

新規依存、CSP変更、SW変更はない。解析木はWorkerの1セット。UIの表示窓は300行、直下詳細10件、詳細本文10,000コードポイント。完了結果は解析キャッシュと分けて保持し、キャッシュ追い出しを理由に削除しない。

## 保持量・操作時間の測定

生の数値は [Chrome](evidence/json-state-retention-chrome.json) / [Edge](evidence/json-state-retention-msedge.json) の合成証跡に記録した。最大入力50MiBの単一文字列、10万ノード、PDF/CSV/標準図と9MiB値を含む完了結果4件を同時に保持。巨大JSON→小さいJSONを3往復し、元Fileの再読込、結果保持、詳細10,000文字、全量DLを検査した。

|指標|Chrome 156.0.8078.74|Edge 156.0.4314.42|
|---|---|---|
|計測点のJS heap＋backing storage合計の最大|183.4 MiB|182.8 MiB|
|巨大JSON追い出し後のJSON Worker減少（GC後、3回）|各約49.99 MiB|各約49.99 MiB|
|50MiB再読込・詳細取得の所要時間|1.55〜2.16秒|1.55〜2.11秒|
|初回変換/表示/DL中の100msタイマー最大間隔|約340ms|約359ms|

修正前の9MiBプレビューでは最大2,846.5msの間隔と計測点373.8MiBを観測した。現在ページだけの解析・特大ソース抜粋に変更した後の値が上表。比較は同じ合成fixtureだが、実行時の負荷差も含む観測値であり、一定の短縮率や待ち時間を保証しない。

クリア後はJSON Workerの不存在と結果0件を確認。既存文書Workerとライブラリ資産の残存は別に記録している。指標はCDPのJS heap/backing storageであり、RSS・File/Blobの全ネイティブ領域・両WASMの全割当・処理中の真の瞬間ピークではない。明示的GC後の減少は診断用であり、製品での即時解放保証ではない。50MiB受付を、20ファイル同時展開や全入力形状の実用性保証と扱わない。

## 失敗分析

- UI実装/負荷観点: 9MiBの完了結果を保持する初期プレビューで、100msタイマーの最大間隔2,846.5msを観測した。全文MarkdownをAST化してから100行に絞る方式を廃し、解析前にページを抽出する方式へ変更。特大ページとplain textは抜粋を明示する方針を設計へ追記し、全量出力を維持する。最終値は負荷証跡で確認する。

- UI実装/観点不足: TabとShift+Tabを交互に押すだけでは末尾の循環を確認できなかった。一方向に15回ずつ進む検査で、末尾からdialog外へ出ることを検出。接続中の起点へ戻す処理に加え、先頭/末尾と非表示フォーカスからのTabをモーダル内へ循環させる。実読み上げの検証とは区別する。

- テスト前提: 負荷ケース初版は通常UIと同じ5秒待ちを使ったが、最大入力は既存の30秒Worker期限で確認すべき範囲だった。処理中表示とtraceを確認し、最大入力だけ実測時間と既存期限を照合した。通常ケースの待ち時間は延長していない。
- 状態前提: 負荷ケース2回目は同一Fileの詳細開閉状態が残る仕様を無視し、「開く」を待った。traceの最後のクリックを確認して、aria-expandedを確認する手順へ修正。クローズ済みCDP接続の後処理例外で元の失敗を隠さないようにした。
- データ問題: 図の単体fixtureでJSX属性の `\\n` と実改行を取り違えた。JS式の文字列へ統一し、同じcodeが再試行へ渡ることを照合した。
- テスト環境: ArrayBufferのinstanceofはjsdom/Nodeのrealm差で失敗するため、モック転送の確認はbyteLengthと読込回数を使った。本番FileReaderの戻り値と取消は別のnative API単体ケースで確認した。
