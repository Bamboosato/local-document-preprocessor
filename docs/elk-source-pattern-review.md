# ELK ソース候補のパス形式と限定したローカル準備

## 観点と前提

まず防ぐべき問題は、実在性不明の情報の混入と、必要なソースを欠いた候補の完全性を誤認すること。機能は指定11領域・版と対応、非機能はローカル再生成・容量・公開境界、データは元 bytes・権利表示・秘密らしい値・パス、UI/報告は検出内容と未確認の区別を検証する。正常・改変/不正パス・空/重複/サイズ境界・候補→判断→公開の状態遷移を分ける。検出パターンは網羅的な個人情報検出ではない。

## 31ファイルの文脈

[検出結果](evidence/elk-pattern-review-7ca.json)には固定 commit、各ファイルの相対パス・hash・サイズ・文脈分類のみを記録し、検出されたパス文字列は記録しない。31件・89一致は、SVG の出力先 metadata / file URI 18件、Eclipse サイトへの URL を含む HTML 7件、ビルド・自動化設定のパス 6件に分かれた。分類は文脈であり、実在性や個人情報該当性の判断ではない。31件すべてについてレビュー要として保持し、元の全体 tar を無条件に公開しない。指定11ソース領域内の該当は0件。

## 11ソース領域を含むローカル候補

既存 `elkjs-0.9.3.zip` に含まれる elkjs 固定版の source・原文・証跡63件をそのまま保持し、ELK 候補 commit の11領域658ファイルと EPL 原文1件を追加した。manifest を含む723件の**ローカル検討用 ZIP**で、Git・`dist` の外にある。旧 ZIP は変更しない。11領域は上流 build.gradle の指定であって、これだけで対応ソースとして必要な全範囲と断定しない。実ビルド時 checkout と生成条件は引き続き未証明。

同一入力・Windows の同一 Python/zlib 環境で別名に4回生成し、ZIP SHA-256 `ee19af9f3d3be729584fcfdf4d08a4c860a5d48fcfb1ce840e4849802d83fbc8` が一致。manifest SHA-256 `a1137f459edce0de048cfbb94936aabe38d69aa4324ed2c54d4cb265df9df0b5`。独立した読取りで CRC・全件 hash・658 blob と上流 tree の一致・既存63件の bytes 不変を確認した。別環境の ZIP 一致や ELK の再ビルド一致を示さない。

独立照合の初回は、EPL 原文 hash の手入力誤りで失敗した。入力値の問題として既存の機械可読追跡記録から期待 hash を取得するよう改めて再実行し、成功した。誤った期待値での失敗と、元ファイルの改変は区別する。合成テストは既存の照合5件と候補生成5件が成功し、危険パス・秘密らしい値・出力先・既存ファイルの上書き・入力 hash 不一致を確認した。文書検査は74文書・325リンク成功。

`python scripts/build_elk_local_candidate.py elkjs-11-roots-review-<新しい名前>.zip` は既存2入力の固定 hash と上流 tree を検査し、11領域・旧候補の指定ファイルを合成する。出力は `tmp/elk-fixed-source-7ca/` の新規名に限定し、上書き・`dist`・公開先への書込みをしない。取得物・旧候補・commit/tree JSON が事前に必要。全選択ファイルのパスと秘密/ローカルパス形式を走査し、一致があれば候補生成を失敗する。この検査は安全性やライセンス条件の完全証明ではない。
